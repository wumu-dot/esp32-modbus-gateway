## 二、R21~R32（设计规范 · 通用芯片/RTOS）

### §2 L1 核心（安全 + 证据，无条件执行）

[MUST][R21] 声称"完成/通过/修好"前必须贴证据（命令输出/串口日志/size 结果），禁止空口白话。
- 编译通过 → 贴 `idf.py build` 的 `Project build complete` ＋ `bin binary size` 行 ＋ `EXIT=0`
- 硬件测试通过 → 贴串口日志（`COM10`）
- bug 修复 → 贴复现前后对比

[MUST][R25] bug/FEAT 的验证结论必须注明**验证条件**（用什么硬件/环境、验证了哪条因果链）。凡"数值非零/链路通"级验证，禁止推断为"功能正常"——功能验证必须扰动输入并观察输出跟随。

### §2 L2 流程规则

[R30] 风险分级执行路径：任务启动时先判断风险等级，按级裁剪流程——
- **重级**（固件代码/硬件参数/算法口径）：全流程（5 阶段 + 每步停等 + R23 评审）
- **中级**（PC 脚本/纯文档）：压缩为 2 步——设计简报→直接做→收尾一次性评审（豁免 R9/R14 中间停等，保留 R21 证据 + R23 评审）
- **轻级**：走 §5 快速路径（机械改动豁免）
- 低风险事项（编码惯例/文件格式）不再上升为确认项，标注"已按惯例处理，有异议再改"即可。

### §3 L3 专项约束

[R26] 调试任何外设/器件问题前，必须先查项目内**预研文档/外部资源索引**中该器件的章节——预研期写下的排查方法**优先于现场推导**。本项目对应：`.workbuddy/memory/判据全集.md`、`docs/spec/`、`docs/hardware/`。**与 R27 的顺序：本条优先，文档无覆盖再外搜。**

[MUST][R27] **预研三源法**——编写新的功能代码前必须先三源核实，缺一不可，只看代码不算完成：
1. **源① 源码内部行为**：调库前必读被调函数源码（官方函数可能有隐藏副作用）。本项目**必须引 `managed_components/` 下的那份**，⛔ 不引 `.reference/`（同版本号也可能内容不同）。
2. **源② Issue 区**：官方/参考仓库 Issues（`github.com/<repo>/issues?q=<关键词>`）——API 误用、边界条件、版本坑往往不在 README 里。
3. **源③ 坑清单交付物**：预研结论必须含"坑与预防"表（**坑 → 后果 → 预防 → 验证判据**），并入 FEAT 文档防御节——**没有坑清单的预研视为未完成**。
纯模板机械改动（改引脚/加外设初始化）可豁免。

[MUST][R28] 抄成熟代码前必须核对**硬件一致性**：
- ✅ 可直接照抄（硬件无关）：协议帧格式、调用流程、数据结构、架构分层
- ❌ 禁止照抄（硬件强相关）：电气参数/时序调优值——上拉驱动强度、时钟树、Baud/超时值等是原作者对其硬件的调优值。此类值必须取**本硬件实测跑通**的来源，注释注明来源与差异
- 优先检索顺序：与本硬件同型号且实测跑通的项目 > 官方仓库 > 高星通用库

[MUST][R29] **设计汇总四件套**：凡 FEAT 进入阶段 2（设计）产出汇总，必须包含以下四部分，缺一不得停等确认：
1. **外部调研**（R27 扩展）：≥2 个同类实现 + 官方库核实，逐项标注"可抄/不可抄"
2. **改动影响地图**（R9 扩展）：实证该变更被谁影响、影响性质，明确"不触什么"与"零冲突面"
3. **算力/资源预算**：CPU 增量、RAM（前后值）、栈、串口带宽——量化数字，禁止"应该没问题"式定性
4. **写入所有相关 FEAT**：不止当前——预研发现影响到的兄弟/父 FEAT 同步更新
格式参照 `docs/features/FEAT-ESPGW-04/05` 的 §2 决策记录（DR）＋ §7 待实测/边界。

[MUST][R31] **编码前预研门控**：任何新增功能性代码（含"看似机械"的小改动）落盘前，必须自问"这个模式的坑我查过三源吗？"——查过才写；没查过先查再写。违反时序的行为须在文档登记"先写后研"偏差并补研闭环。纯 §5 快速路径（改宏/注释/路径）豁免。

[MUST][R32] **完整研发操作流程（总纲）**——"三源法"的端到端执行载体。任何功能性开发按此八步推进，步骤③⑤⑥⑦⑧涉及外部来源时遵循 R27/R28 口径。**缺任一步骤需在 FEAT 文档登记偏差。**
1. **预研**：找正确、成熟方案。来源池 = 官方仓库 + 权威个人平台 + 本项目预研文档，至少对照 1~2 个实现。
2. **排雷**：查 Issue 区（官方 + 参考实现）看已知坑——API 误用、边界条件、版本坑（R27 源②）。
3. **预防**：把"坑→后果→预防→验证判据"写成坑清单（R27 源③），并入设计汇总防御节。
4. **影响分析**：列出改动影响——**是否影响前面已有的内容**（不兼容？破坏地基？），用影响地图明确"不触什么"与零冲突面（R9/R29②）。
5. **资源预算**：占用多少资源（CPU/RAM/栈/串口带宽），量化（R29③）。
6. **复用**：按 R28 核对硬件一致性，能照抄的照抄、禁止照抄的另取本硬件实测来源。
7. **遇意外**：去权威技术网站找答案 + `grep` 交叉确认根因（R21 证据：修复须带复现前后对比 + 验证条件 R25）。
8. **审查**：最后 review（R23，按 AC 逐条打勾），通过才标记完成。

### §4 冲突仲裁

**安全红线（R19/R20）> 完整流程总纲（R32）> 验证证据（R21/R25）> 流程停等（R9/R14/R23）> 三源调研（R27/R28/R29）> Token 优化（R4/R22/R1）**
